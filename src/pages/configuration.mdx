<Section heading="Project configuration: config.yaml" surface={false}>

  <Fragment slot="sub">

    A project's own settings: the coding agent it drives, where it stores
    specs, plans, and changelog records, its shared knowledge stores, and the
    repositories it registers as members. Every project has exactly one
    `.spektacular/config.yaml`, at the root of the project. The file is
    created by `spektacular init`, missing keys fall back to defaults, and
    `${VAR}` patterns are expanded from the environment when `config.yaml`
    or `repo.yaml` is read. A complete example, declaring one shared knowledge
    store alongside the store each registered repository brings with it:

  </Fragment>

  ```yaml
  schema: 3                       # settings format version; `migrate` raises it
  written_by: 0.16.0              # the Spektacular version that last wrote this file
  skills_version: 0.16.0          # the Spektacular version that installed the agent skills

  command: spektacular
  agent: claude
  spec_trigger_threshold: moderate

  debug:
    enabled: false

  spec:
    provider: file
    id_method: timestamp
    config:
      directory: specs            # relative to the folder holding `config.yaml`

  plan:
    provider: file
    config:
      directory: plans

  changelog:
    provider: file
    config:
      directory: changelog

  knowledge:
    sources:                        # the project's shared stores only; each
      - name: team                  # repository declares its own in repo.yaml
        provider: file
        config:
          location: ${HOME}/work/team-knowledge   # or ../../team-knowledge,
                                                  # relative to this file

  design:
    sources:                        # where the project's design documents live;
      - name: api                   # declared by the project, never by a repository
        provider: file
        config:
          location: ../design/api   # relative to this file; may sit outside the project

  repos:
    - name: docs
      location: ../../docs/.spektacular
  ```

</Section>

<ConfigurationKeys heading="Project configuration keys" surface={true}>

  <Fragment slot="sub">

    Thirteen top-level keys control the tool from `.spektacular/config.yaml`:
    `schema`, `written_by`, `skills_version`, `command`, `agent`,
    `spec_trigger_threshold`, `debug`, `spec`, `plan`, `changelog`,
    `knowledge`, `design`, and `repos`.

  </Fragment>

  <ConfigKey name="schema" type="integer" defaultValue="written by Spektacular">

    The settings format version. Never edit it by hand; `migrate` raises it.
    A file with no `schema` is read as the oldest format and needs an
    upgrade, as described under Upgrading a project below.

  </ConfigKey>

  <ConfigKey name="written_by" type="string" defaultValue="written by Spektacular">

    The Spektacular version that last saved this file. Informational only:
    it never triggers an upgrade, so a file written by a different version
    of the same format is left alone.

  </ConfigKey>

  <ConfigKey name="skills_version" type="string" defaultValue="written by Spektacular">

    The Spektacular version that last installed your agent skills. Only
    `init` and `migrate` set it, so rewriting the file for any other reason,
    registering a repository for example, leaves it untouched. When it
    differs from the running Spektacular, commands stop until you upgrade.

  </ConfigKey>

  <ConfigKey name="command" type="string" defaultValue="<code>spektacular</code>">

    The CLI command name used in agent-generated documentation. Almost never
    needs to change, kept configurable so downstream tooling can refer to a
    different binary name if your team wraps the tool.

  </ConfigKey>

  <ConfigKey name="agent" type="string" defaultValue="set by <code>spektacular init &lt;agent&gt;</code>">

    Which coding agent to drive during the implement workflow. Supported
    values: `claude` (Claude Code), `bob`, and `codex`. New agents register
    via the [Agent plugin interface](/plugins/).

  </ConfigKey>

  <ConfigKey name="spec_trigger_threshold" type="string" defaultValue="<code>moderate</code>">

    How readily the agent offers to capture an open-ended discussion as a
    spec mid-conversation, rather than waiting for you to run `/spek-new`.
    One of `strict` (only substantial, multi-requirement features),
    `moderate` (default: a clear scoped decision or a feature with more
    than one requirement), or `lenient` (offers readily, including small
    fixes). Read live at the moment the agent decides whether to offer, so a
    change here takes effect immediately, mid-conversation.

  </ConfigKey>

  <ConfigKey name="debug" type="section" defaultValue="<code>debug.enabled: false</code>">

    Debug logging. Set `debug.enabled: true` to write a JSONL log of every
    command to `.spektacular/debug/session-log.jsonl`, useful when reporting
    issues or developing a new plugin. See the [Debugging](/debugging/) page
    for the full walkthrough.

  </ConfigKey>

  <ConfigKey name="spec" type="section" defaultValue="file provider, timestamp IDs, <code>specs</code>">

    How specs are stored and identified.

    - `spec.provider`: storage backend; only `file` ships today.
    - `spec.id_method`: spec naming scheme. One of `timestamp` (default),
      `counter` (sequential numbers), or `external` (the caller supplies an
      `id` with each spec).
    - `spec.config.directory`: where the file provider writes specs. Defaults
      to `specs`, relative to the folder holding `config.yaml` (the same rule as
      `repos[].location`), so specs land in `.spektacular/specs`. A directory
      outside the project is refused.

    Every spec record also carries lifecycle metadata: a created date, a
    document status, and, once resolved, a closed date, tracked automatically
    without any extra configuration.

  </ConfigKey>

  <ConfigKey name="plan" type="section" defaultValue="file provider, <code>plans</code>">

    How plans are stored.

    - `plan.provider`: storage backend; only `file` ships today.
    - `plan.config.directory`: where the file provider writes plans. Defaults
      to `plans`, relative to the folder holding `config.yaml`, so plans land in
      `.spektacular/plans`.

    Every plan record also carries lifecycle metadata: a created date, a
    document status, and, once resolved, a closed date, tracked automatically
    without any extra configuration.

  </ConfigKey>

  <ConfigKey name="changelog" type="section" defaultValue="file provider, <code>changelog</code>">

    How completed-feature changelog records are stored.

    - `changelog.provider`: storage backend; only `file` ships today.
    - `changelog.config.directory`: where the file provider writes changelog
      records. Defaults to `changelog`, relative to the folder holding
      config.yaml, so records land in `.spektacular/changelog`.

    A record is written automatically at the end of every `implement` run,
    one flat markdown file per feature, covering what was built, why it
    matters, and how the outcome differed from the plan. Every changelog
    record also carries the same lifecycle metadata as specs and plans: a
    created date, a document status, and, once resolved, a closed date.

  </ConfigKey>

  <ConfigKey name="knowledge" type="section" defaultValue="none">

    Ordered list of the shared knowledge stores the project itself owns, such
    as a team handbook. Each repository declares its own store in its
    `repo.yaml`, not here.

    - `knowledge.sources[].name`: the name this store is addressed by. Must be
      unique among the project's own stores.
    - `knowledge.sources[].provider`: storage backend; only `file` ships
      today.
    - `knowledge.sources[].config.location`: where the file provider reads
      knowledge from. Relative paths resolve from the folder holding
      `config.yaml`, the same base a `repos` entry uses.

  </ConfigKey>

  <ConfigKey name="design" type="section" defaultValue="none">

    Ordered list of the design sources the project declares. A design document
    holds the worked design a feature is built to, and a spec references one
    rather than restating it. Design sources are declared by the project only;
    a repository does not declare its own.

    - `design.sources[].name`: the name this source is addressed by. Must be
      unique among the project's design sources.
    - `design.sources[].provider`: storage backend; only `file` ships today.
    - `design.sources[].config.location`: where the file provider reads and
      writes design documents. Relative paths resolve from the folder holding
      `config.yaml`, the same base a `repos` entry uses. The location may sit
      outside the project, and is never rewritten on save.

    A source can hold both kinds of design document side by side. A design your
    team already had is stored exactly as supplied, gaining no frontmatter and
    never being reformatted; a design Spektacular authors with you carries the
    same lifecycle record every spec and plan carries.

    See the [Design Documents](/design-documents/) page for the full reference.

  </ConfigKey>

  <ConfigKey name="repos" type="section" defaultValue="none">

    How a project registers its member repositories. Each entry names one
    repository and locates the folder that holds the repository's own
    `repo.yaml`:

    - `repos[].name`: the repository's project-local name, unique within
      this project and slug-safe; plans and changelog entries refer to
      repositories by it.
    - `repos[].location`: the folder holding the repository's `repo.yaml`,
      absolute or relative to the folder holding this `config.yaml`.
      Nothing is appended to it, so the project's own footprint is `.` and
      a repository folder inside the project is `../repos/<name>`. The
      older `local` key is still accepted and means the same thing; it is
      written back as `location`.
    - `repos[].provider`: the repository's provider. Only `git` ships today.
    - `repos[].dependencies`: the project-local names of other registered
      repositories this one depends on.

    Where the repository's code lives is the repository's own concern,
    declared by `source` in its `repo.yaml` (below). The older `address`
    key is no longer accepted here: a configuration that still carries it
    fails to load with an error naming the repository, and its value moves
    to that repository's `source`.

    A repository's description, role, and tags are not declared
    here either. They live in the repository's own configuration file,
    described below.

  </ConfigKey>

</ConfigurationKeys>

<Section heading="Repository configuration: repo.yaml" surface={false}>

  <Fragment slot="sub">

    What a member repository is: its description, role, tags,
    where its code lives, and its own knowledge sources and changelog
    provider. Every member repository carries its own `repo.yaml`,
    distinct from the project's own `.spektacular/config.yaml` above. The
    folder holding that file is the repository's location, and the `source`
    key says where its code is, relative to that same folder. It is created
    as part of the repository's footprint, either when it is registered
    with `repo add` or during a project's initialization cascade over its
    already-registered repositories. It carries no reference back to any
    project that registers it, so the same repository can belong to any
    number of projects while describing itself in exactly one place. A
    complete example, for a documentation site:

  </Fragment>

  ```yaml
  schema: 2                        # settings format version; `migrate` raises it
  written_by: 0.16.0               # the Spektacular version that last wrote this file

  description: Marketing and documentation site, built with Astro
  role: documentation
  tags:
    - docs
    - website
  source:
    provider: file                   # file or git
    config:
      location: ..                   # or git@github.com:org/docs.git for git

  knowledge:
    provider: file
    config:
      location: knowledge

  changelog:
    provider: file
    config:
      directory: changelog
  ```

</Section>

<ConfigurationKeys heading="Repository configuration keys" surface={true}>

  <Fragment slot="sub">

    Descriptive metadata, the location of the repository's code, and the
    repository's own knowledge sources and changelog provider, shown
    wherever this repository's details are surfaced, such as
    `spektacular repo list` or the repository roster an agent sees during
    planning and implementation. Every relative path in this file, the
    source included, resolves from the folder holding the file.

  </Fragment>

  <ConfigKey name="schema" type="integer" defaultValue="written by Spektacular">

    The settings format version of this `repo.yaml`, on its own count: a
    repository file at format 2 sits beside a project file at format 3.
    `migrate` raises it for every registered repository present on disk.

  </ConfigKey>

  <ConfigKey name="written_by" type="string" defaultValue="written by Spektacular">

    The Spektacular version that last saved this file, for diagnosis only.

  </ConfigKey>

  <ConfigKey name="description" type="string" defaultValue="none">

    A short account of what this repository is or does.

  </ConfigKey>

  <ConfigKey name="role" type="string" defaultValue="none">

    The role this repository plays, such as `service`, `documentation`, or
    `library`.

  </ConfigKey>

  <ConfigKey name="tags" type="list of strings" defaultValue="none">

    Free-form labels for the repository, such as `docs`, `website`, or
    `backend`.

  </ConfigKey>

  <ConfigKey name="source" type="string" defaultValue="the directory holding <code>.spektacular/</code>">

    Where this repository's code lives. Either a file location (a plain
    path or a `file://` path, absolute, relative to the directory holding
    `repo.yaml`, or using `${VAR}`) or a git location (`git://`, `ssh://`,
    `https://`, or `user@host:path`). A git location is cloned into the
    project's `.spektacular/repos/<name>/` folder the first time the
    repository is used and never fetched or pulled afterwards. When set,
    `repo list` reports it as the repository's `root` and workflows send
    agents there; knowledge and changelog entries still land where this
    file's `knowledge` and `changelog` keys say, under the folder holding
    `repo.yaml`. Leave it unset when the repository's Spektacular files
    sit inside its code. Not to be confused with the project-level
    `source` in `config.yaml`, which records a git address for changelog
    provenance only.

  </ConfigKey>

  <ConfigKey name="knowledge" type="section" defaultValue="a file store at <code>knowledge</code>">

    This repository's single knowledge store, holding what is true of its own
    code. The store is addressed by the name the project registered this
    repository under, so there is no name to set here and no more than one
    store to declare.

    - `knowledge.provider`: storage backend; only `file` ships today.
    - `knowledge.config.location`: where the file provider reads this
      repository's knowledge from. Relative paths resolve against the folder
      holding `repo.yaml`.

    See the [Knowledge Base](/knowledge-base/) page for the full reference.

  </ConfigKey>

  <ConfigKey name="changelog" type="section" defaultValue="file provider, <code>changelog</code>">

    Same shape as the project-level `changelog` key above, resolved from
    the folder holding this file; this is where the repository's own
    derived changelog entries land.

  </ConfigKey>

</ConfigurationKeys>

<Section heading="Upgrading a project: migrate" surface={false}>

  <Fragment slot="sub">

    Every settings file records the format version it was written in. When a
    release changes that format, or when you install a newer Spektacular than
    the one that installed your agent skills, commands stop with an error
    naming `migrate` until the project is brought up to date. `migrate`,
    `init`, `version check` and `help` always run, so the way out is always
    reachable.

  </Fragment>

  Preview every change first, which touches nothing on disk:

  ```bash
  spektacular migrate --dry-run
  ```

  Then apply it:

  ```bash
  spektacular migrate
  ```

  One run:

  - upgrades `config.yaml` and every registered repository's `repo.yaml`
    present on disk, through as many formats as each file is behind
  - keeps a `.v<N>.old` copy of each file it rewrites, named after the
    format the file started at
  - skips repositories that are not checked out locally and names each one;
    they are upgraded the next time they are set up
  - reinstalls the agent skills when they are older than the running
    Spektacular, and records the new version only once that install succeeds

  Re-running `spektacular init <agent>` applies the same upgrades before it
  does anything else, so an existing project can also be brought current by
  setting it up again. A file written by a *newer* Spektacular is refused
  rather than converted: the error asks you to update Spektacular, and the
  file is never rewritten.

</Section>
