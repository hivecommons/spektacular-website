## Logging is on by default

Every `spektacular` command run in a project is recorded to
`.spektacular/logs/`, with nothing to switch on. The folder is already
ignored by git: `spektacular init` adds it to `.spektacular/.gitignore`,
`spektacular migrate` adds it to projects set up by an earlier version, and
the folder holds its own `.gitignore` as well, so logs are never committed
by accident.

The `log` section of `.spektacular/config.yaml` controls it:

```yaml
log:
  provider: file        # the logger; only file ships today
  level: standard       # off | standard | verbose
  retention: 10         # most recent workflow runs kept
  config:
    directory: logs     # relative to the folder holding config.yaml
```

Nothing is recorded outside a project, so a command run in a repo's code
checkout never leaves a log behind.

## What each level records

- `standard` (the default): for each command, its name and arguments, the
  run it belongs to, the agent, the workflow and the step it ran in (and the
  step it moved the workflow to), when it started and ended, its exit status
  and, when it failed, the error message. It keeps no responses, so the log
  stays small.
- `verbose`: everything `standard` records, plus the command's full response
  and the workflow state before and after it, as debug mode did. Use it when
  reporting an issue or reproducing a problem; verbose logs grow quickly.
- `off`: nothing is recorded. To switch logging off, set
  `log.level: off` in `.spektacular/config.yaml`.

## Where logs go

Each workflow run gets a file of its own, named for when the run started,
the agent the project is set up for, and the workflow, for example
`20261024T090334.911373161Z_claude_plan_000008_debugging-docs.jsonl`. Every
command of that run lands in it, across interruptions and resumes. When an
epic is planned or implemented, each spec's workflow is its own run, so
specs worked on side by side never share a file. Restarting a workflow with
`--force` starts a new run and a new file.

Commands run while no workflow is in progress go to one file per day, for
example `standalone_20261024.jsonl`.

To write logs somewhere else, set `log.config.directory`. A relative path is
resolved from the folder holding `config.yaml` (`.spektacular/`); an
absolute path is used as written.

## How long logs are kept

Spektacular keeps the logs of the 10 most recent workflow runs, or the
number set in `log.retention`, and deletes older ones when a new run starts.
Days of standalone commands are counted separately, with the same number of
most recent days kept, so a burst of standalone commands never pushes out a
workflow run's log. A log that cannot be deleted is skipped: logging never
changes a command's output or exit code.

## Commands that are never logged

`spektacular status` is never logged, at any level, so editors and tools
that poll it every few seconds do not fill the log. Commands that only
report on the project or its logs are never logged either: the run
statistics reports of `spektacular stats`, and every form of them, leave no
record, so a report never adds to or trims the logs it reads.

The level is set in `config.yaml` only: there is no environment variable for
it.

## Reading a record

Each line is one JSON record following the OpenTelemetry trace data model.
Here is a `standard` record of a `spec goto`:

```json
{
  "record": "span",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "name": "spec goto",
  "kind": "internal",
  "start_time": "2026-10-24T09:03:34.911373161Z",
  "end_time": "2026-10-24T09:03:34.934002113Z",
  "status": { "code": "ok" },
  "attributes": {
    "spektacular.span.type": "command",
    "spektacular.agent": "claude",
    "spektacular.workflow.kind": "spec",
    "spektacular.workflow.name": "000073_log-mode",
    "spektacular.step": "interview",
    "spektacular.step.to": "overview",
    "process.command_args": ["spec", "goto", "--data", "{\"step\":\"overview\"}"],
    "process.exit_code": 0
  },
  "resource": { "service.name": "spektacular", "service.version": "0.21.0" }
}
```

- `trace_id`: the run the command belongs to. Every command of one workflow
  run shares it; a command outside any workflow gets its own.
- `span_id`: this command's own id.
- `name`: the command, such as `spec goto`.
- `start_time` / `end_time`: when the command started and ended, in UTC.
- `status`: `ok`, or `error` with the error `message`.
- `attributes`:
  - `spektacular.agent`: the agent named in `config.yaml`, or `unknown`.
  - `spektacular.workflow.kind` / `spektacular.workflow.name`: the workflow,
    absent for a command outside one.
  - `spektacular.step`: the step the command ran in.
  - `spektacular.step.to`: the step it moved the workflow to, when it moved.
  - `process.command_args`: the arguments the command was run with.
  - `process.exit_code`: the command's exit code.
  - At the `verbose` level, also `spektacular.response` (the full output)
    and `spektacular.state.before` / `spektacular.state.after`.

A step's duration is the time between the commands that moved the workflow
onto it and off it again.

## Upgrading from debug mode

Debug mode is replaced by logging. `spektacular migrate` turns
`debug.enabled: true` into `log.level: verbose`, and `false` (or no debug
setting) into `standard`. Old files in `.spektacular/debug/` are left where
they are, untouched; delete them when you no longer need them.
